# API для Mini App

Локальная база URL: `http://127.0.0.1:3001`. Все ответы — JSON, кроме успешных операций записи в план (204). Каталог доступен без входа. Личный план требует `Authorization: Bearer <accessToken>`.

Контракты: `packages/contracts/src/index.ts`. Фронтенд `apps/web` использует зависимость `@olimp/contracts: workspace:*` и проверяет ответы общими схемами. Объект можно проверить через `OlympiadDetail.parse(json)`, тип получить через `z.infer<typeof OlympiadDetail>`.

Карточки каталога, плана и чата содержат `calendarRaw`, `level`, `levelProfile`, `levelStatus`, `levelSourceUrl`. Поля опциональны для совместимости со старым API. Значения уровня и его статуса берутся из новых столбцов CSV; «—» означает, что уровень не указан. Проект перечня не считается утверждённым уровнем. Показывайте текст `calendarRaw` и `statusRaw` даже при `nextEvent=null`: внутренний статус проверки ограничивает только расчёт событий, а не отображение исходных данных. Каталог и фильтры включают только `inCatalog=true`; подробная карточка и сохранённые планы доступны и для скрытых записей.

## Маршруты

| Метод | URL | Что возвращает / делает |
| --- | --- | --- |
| GET | `/health` | Проверяет подключение к PostgreSQL |
| GET | `/olympiads/filters` | Значения фильтров, подписи и общие количества |
| GET | `/olympiads` | Карточки, `total`, `page`, `pageSize` |
| GET | `/olympiads/:id` | Полная информация, все исходные поля и этапы, серия, профили перечня и льготы вузов |
| GET | `/series/:slug` | Олимпиада-серия: общий уровень, профили РСОШ, этапы из справочника, карточки каталога, льготы |
| GET | `/universities` | Вузы из справочника льгот: сколько серий и карточек дают в них льготу |
| GET | `/universities/:slug` | Льготы вуза по олимпиадам: БВИ / 100 баллов, порог ЕГЭ, ID подходящих карточек |
| POST | `/auth/max` | Принимает `{ "initData": "..." }`, возвращает JWT |
| POST | `/auth/dev` | Локальный демонстрационный вход, только если включён |
| GET | `/me` | Профиль текущего пользователя |
| POST | `/me/registration` | Первое заполнение профиля; повторное — 409 |
| PATCH | `/me/profile` | Изменение учебных предпочтений текущего пользователя |
| DELETE | `/me` | Удаляет аккаунт: профиль, предметы и план (каскадно); ответ 204, старый токен после этого получает 401 |
| GET | `/me/plan` | Сохранённые олимпиады, заметки, этапы |
| PUT | `/me/plan/:id` | Добавляет олимпиаду в план, тело не требуется |
| PATCH | `/me/plan/:id` | Меняет `tracking` и/или `note` |
| DELETE | `/me/plan/:id` | Удаляет из плана |
| GET | `/me/plan/events?days=90` | Подтверждённые события отслеживаемых олимпиад |

PUT и DELETE идемпотентны: повторный вызов не создаёт дубликаты. Повторный PUT сохраняет прежние заметку и переключатель отслеживания. Чтобы возобновить отслеживание, отправьте PATCH с `tracking: true`.

## Поиск и фильтры

Пример: `/olympiads?q=высшая%20проба&grades=9,10&formats=hybrid&page=1&pageSize=20`.

| Параметр | Значения |
| --- | --- |
| `q` | До 200 символов; все слова должны встречаться в названии, предметах, организаторе или описании |
| `subjectIds` | ID из `/olympiads/filters`, например `1,5`; несколько предметов означают «любой из них» |
| `grades` | Классы `1..11`, например `8,9`; проверяется вхождение в диапазон участников |
| `formats` | `onsite`, `online`, `hybrid`, `unknown` |
| `levels` | `I`, `II`, `III`, `I–II`, `II–III`, `I–III`, `ВсОШ`, `unknown`; уровень карточки (см. ниже), `unknown` — уровня нет |
| `universities` | slug вузов из `/universities`, например `mipt,hse`: только карточки с уровнем, чья олимпиада даёт льготу в одном из вузов |
| `series` | slug серий, например `ranepa`: все предметные карточки этих олимпиад |
| `participation` | `individual`, `team`, `mixed`, `unknown` |
| `scheduleStatus` | `published`, `unknown`, `not_held` |
| `sort` | `rating` (по убыванию; по умолчанию) или `name` |
| `page` | От 1 до 10000, по умолчанию 1 |
| `pageSize` | От 1 до 100, по умолчанию 20 |

Можно передавать списки через запятую или повторные параметры. Разные фильтры соединяются через **И**, значения внутри одного фильтра — через **ИЛИ**. Олимпиады без диапазона классов не попадают в фильтр по классу. Без фильтра они доступны. Счётчики `/filters` относятся ко всему каталогу, а не к текущей комбинации фильтров.

Поиск не зависит от регистра, различия е/ё, кавычек и пунктуации. Это поиск по словам/подстрокам, без исправления опечаток и без морфологического анализа. Сортировка имеет дополнительный ключ ID для стабильной пагинации. Пустая страница даёт `items: []`, сохраняя общее `total`.

## Карточка и календарь

В списке есть название, описание (либо `null`), предметы, классы, формат, тип участия, исходный рейтинг, статус, источник, `calendarState` и `nextEvent`. Это рейтинг источника, не уровень РСОШ и не наша оценка.

Краткие карточки также содержат `organizers` — список организаторов из базы. Поле необязательное в контракте для совместимости с прежними ответами и сохранёнными демоданными; текущий сервер возвращает его всегда.

Подробная карточка дополнительно содержит:

- `organizers`, `contacts`, `documents` — списки текстовых значений;
- `featuresRaw`, `calendarRaw`, `scheduleUpdatedRaw` — исходные тексты;
- `rawSource` — все 19 оригинальных столбцов CSV с русскими ключами;
- `stages` — выделенные из CSV этапы и отдельно проверенные этапы;
- `importedAt` — когда запись импортировали в нашу базу, а не когда организатор проверил расписание;
- `seriesInfo` — серия: общий уровень, формат, признак качества расписания (`ok`, `placeholder`, `outdated`, `hidden`) и профили перечня РСОШ с уровнями и направлениями подготовки;
- `benefits` — `{ applicable, note, items }`: льготы вузов (`university`: `slug`, `name`, `city`, `fullName`; `kind`: `bvi` | `score_100`, `diploma`: `any` | `winner`, `minScore`, `maxScore`, `requirement`). `applicable=false` и пустой `items`, если профиль карточки не входит в перечень;
- `catalogCalendarRaw` — исходный текст расписания olimpiada.ru, даже если `calendarRaw` показывает расписание справочника.

## Справочник: уровень, серия и расписание

Данные из `data/reference` (подробно — [data/reference/README.md](../data/reference/README.md)) добавляют к карточкам и деталям:

- `series: { slug, name } | null` — к какой олимпиаде-серии относится предметная карточка;
- `level`, `levelProfile`, `levelStatus`, `levelSourceUrl` — уровень хранится в столбцах базы. `levelSource`: `rsosh_list` — по профилю из файла перечня, `catalog` — из выгрузки olimpiada.ru, `series` — общий уровень серии. `level: null` — уровня нет, причина в `levelStatus`;
- `scheduleSource`: `reference` — `calendarRaw` и основные этапы взяты из `olympiads_clean`; `catalog` — расписание olimpiada.ru (шаблонные или прошлогодние даты справочника либо расхождение с датами карточки);
- `stages[].origin`: `csv` (olimpiada.ru), `reference` (справочник, с `mode`: `online` | `onsite` | `mixed`), `verified_import` (проверенные даты). Этапы справочника всегда `unverified` и не создают `nextEvent`.

Неизвестные данные представлены `null`, пустыми списками или значением `unknown`. Во фронтенде выводите текстовые поля как текст, не как HTML. Названия документов не содержат адресов скачивания. Контакты могут включать неполные URL.

| `calendarState` | Внутренний смысл для расчёта событий |
| --- | --- |
| `unknown` | Расписание пока неизвестно |
| `unverified` | Даты требуют уточнения года и проверки источника |
| `verified` | Есть ближайшее событие с проверенной датой |
| `needs_review` | Расписание изменилось; даты требуют повторной проверки |
| `no_upcoming` | В проверенных датах нет будущих событий |
| `not_held` | По данным выгрузки олимпиада не проводится |

`verified` относится к конкретным загруженным датам и не означает, что весь календарь заполнен. `nextEvent` может быть концом уже начавшегося этапа. При частичной повторной проверке `needs_review` может сочетаться с `nextEvent` другого, ещё подтверждённого этапа. Для олимпиады со статусом `not_held` события всегда скрываются.

Форма `nextEvent`:

```ts
{
  stageId: string;
  name: string | null;
  date: string;                  // YYYY-MM-DD
  kind: 'starts' | 'ends';
  timezone: 'Europe/Moscow';
  sourceUrl: string;
}
```

Дата окончания включительна: событие за сегодняшний день остаётся видимым до смены календарного дня в Москве. Если известно только окончание, API не выдумывает дату начала и не утверждает, что этап уже идёт. Однодневный этап может иметь два события: начало и окончание. Для одинаковой даты `nextEvent` отдаёт приоритет окончанию как дедлайну.

## Подключение к MAX

```ts
const response = await fetch(`${API}/auth/max`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ initData: window.WebApp.initData }),
});
if (!response.ok) throw new Error('Не удалось войти');
const { accessToken } = await response.json();

await fetch(`${API}/me/plan/88`, {
  method: 'PUT',
  headers: { Authorization: `Bearer ${accessToken}` },
});
```

Сервер проверяет HMAC-SHA256, отсутствие повторных параметров, `auth_date` (не старше часа, допустимое отклонение часов вперёд — 30 секунд) и данные пользователя. Возвращает `{ accessToken, expiresIn: 3600 }`. JWT храните в памяти клиента, после истечения обновляйте вход из актуальных стартовых данных MAX. При устаревшем `initData` нужно переоткрыть Mini App. Идентификатор пользователя в запросах к плану передавать не нужно: сервер получает его из JWT.

Локальный вход: POST `/auth/dev` без тела. Все такие входы относятся к одному демонстрационному аккаунту. Маршрут отсутствует, если `ALLOW_DEV_AUTH=false`.

## Личный план

PATCH `/me/plan/88`:

```json
{ "tracking": true, "note": "Подготовить документы" }
```

Оба поля необязательны, но нужно хотя бы одно. `note` — до 2000 символов, `null` удаляет заметку. `tracking=false` оставляет олимпиаду в сохранённых, исключая её из `/me/plan/events`. Сам план сортируется по ближайшему событию активных подписок; записи без него идут в конце.

Каждая запись `GET /me/plan` содержит `calendarEvents` — датированные моменты расписания, которое показывает карточка: `{ stageId, name, stageKind, kind: starts | ends | day, date, estimated }`. `starts`/`ends` — начало и конец этапа, `day` — однодневный этап. Если в источнике нет года, он берётся из учебного сезона, в котором проверялось расписание (1 августа — 31 июля), и `estimated=true`; для завершённого цикла («итоги опубликованы», «следующий цикл ожидается») такие даты не выводятся. На этих событиях построен календарь плана и счётчик «скоро»; напоминаний они не создают.

`GET /me/plan/events?days=90` возвращает `from`, `through`, `items`. Диапазон включает сегодня и следующие 89 дней; разрешено от 1 до 366 дней. Каждое событие содержит поля `nextEvent` плюс `olympiadId` и `olympiadTitle`. Если проверенных будущих дат нет, возвращается пустой список. Клиент должен отдельно показать сохранённые олимпиады без расписания из `/me/plan`.

## Ошибки

Ошибка содержит `error` и `message`. Основные статусы: 400 — параметры не прошли проверку, 401 — требуется вход, 404 — запись не найдена, 429 — превышен лимит, 503 — вход MAX не настроен. Детали внутренней ошибки не передаются клиенту.

Ограничение запросов: 120 в минуту на IP, вход MAX — 20. Перед эксплуатацией за reverse proxy настройте доверенные прокси и общий лимитер при нескольких экземплярах API. В текущей реализации лимит хранится в памяти одного процесса.

## Чат с Олимпом

`POST /assistant/chat` требует `Authorization: Bearer <accessToken>`, как личный план. Секрет DeepSeek находится только на сервере.

```json
{
  "message": "Подбери олимпиады по информатике для 9 класса",
  "history": [
    { "role": "user", "content": "Привет", "olympiadIds": [] },
    { "role": "assistant", "content": "Какой предмет тебя интересует?", "olympiadIds": [] }
  ]
}
```

`message`: 1–2000 символов после удаления крайних пробелов. `history` необязательна, не более 10 реплик; каждая содержит `role=user|assistant`, `content` до 4000 символов и необязательный `olympiadIds` (до 5 ID карточек прошлой реплики). Всего не более 12 000 символов. Поля `userId`, системные сообщения и другие лишние поля отклоняются.

Ответ `200`: `{ "message": "Текст ответа", "olympiads": [...] }`, где `olympiads` — до пяти существующих `OlympiadCard`. `Cache-Control: no-store`. ID переписки отсутствует: сервер не сохраняет историю, клиент передаёт последние реплики.

Если в базе нет ответа, сообщение заканчивается фразой «Сейчас поищу в интернете…», а ответ содержит `webSearch: { token, question, olympiadIds }`. `question` — самостоятельный вопрос с учётом истории (сленг раскрыт), `olympiadIds` — олимпиады каталога, о которых идёт речь (может быть пустым для вопросов о вузе или правилах). Согласие пользователя не требуется: клиент сразу отправляет `token` в `/assistant/web-search` и показывает индикатор поиска. Ответ по базе вопросов об олимпиадах (`data/faq`) приходит с `webSources` вида `kind=faq` — официальные источники этих ответов.

`POST /assistant/web-search` с той же авторизацией принимает строго `{ "token": "<token из ответа чата>" }`. Токен — подписанный сервером билет на 15 минут, связанный с текущим пользователем, вопросом, ID олимпиад и вузов. Клиент не задаёт ни вопрос, ни URL. Ответ содержит `message`, пустой `olympiads`, `webSources: [{ title, url, checkedAt, kind }]` и `webDisclaimer`. Предупреждение обязательно показывать вместе с ответом; `checkedAt` — дата получения сведений, а не публикации. `kind=page` — прочитанная HTML-страница, `kind=pdf` — прочитанный PDF-документ. Сведения из интернета не записываются в подтверждённое расписание.

Поисковый сервис не используется. Сервер открывает только известные адреса: страницу олимпиады на olimpiada.ru и сайт организатора из карточки каталога, а также список ссылок `data/assistant/university_links_descriptions.csv` (сайты и правила приёма вузов, РСОШ, каталоги олимпиад, рейтинги). DeepSeek выбирает до пяти адресов по описаниям, сервер читает до трёх (остальные — если первые недоступны) и при необходимости один раз переходит по ссылке, найденной на прочитанной странице (например, на PDF правил приёма). Ключей не нужно. Лимит — 6 запросов в минуту на пользователя; занятость общая с `/assistant/chat`. Сервер ограничивает поиск 100 секундами, клиент ждёт до 110. Неверный или истёкший билет — `400 WEB_SEARCH_EXPIRED`, ответ без корректных источников — `502 WEB_SEARCH_INVALID_ANSWER`. Если сайты недоступны, приходит обычный ответ `200` с объяснением и пустым `webSources`.

Ошибки используют `{ "error", "message" }`: `400` — входные данные, `401` — вход, `429` — лимит/занятость, `502` — некорректный ответ модели, `503` — сервис не настроен/недоступен, `504` — время ожидания. Максимум 10 запросов в минуту на пользователя, один активный запрос на пользователя. Не повторяйте запрос автоматически: повтор инициирует пользователь.

Чат только читает данные. Сохранение из карточки — отдельный существующий `PUT /me/plan/:id`; текст ответа модели никогда не считается подтверждением выполненного изменения. Подробности: [ASSISTANT.md](ASSISTANT.md).

## Профили

Ответ `/auth/max` и `/auth/dev`: `{ accessToken, expiresIn: 3600, user: UserProfile }`. `user.registeredAt === null` — профиль ещё не заполнен. `GET /me` возвращает тот же `UserProfile`: `id`, `maxUserId`, `name`, `avatar` (data URL JPG/PNG/WebP до 1 МБ или `null`), `grade`, `region`, `subjects` (ID предметов), `online`, `onsite`, `registeredAt`, `createdAt`.

`POST /me/registration` принимает все поля предпочтений: `{ name, grade, region, subjects, online, onsite }`; класс допускает `null`, город — пустую строку, предметы — пустой массив. `PATCH /me/profile` принимает непустое подмножество этих полей и необязательное `avatar`: data URL JPG/PNG/WebP до 1 МБ, `null` удаляет фото. Если поле не передано, фото сохраняется. Ограничение тела этого маршрута — 1 500 000 байт; формат, сигнатура и размер фото проверяются общим контрактом. Фото доступно только в авторизованных ответах профиля с `Cache-Control: no-store`. Ответ — обновлённый `UserProfile`. Имя: 1–80 символов после обрезки пробелов; класс: 1–11; регион: до 100 символов; до 35 уникальных существующих предметов. Поля идентичности с клиента запрещены. Обе операции требуют JWT.

`400` — неверные поля или неизвестный предмет. `409 ALREADY_REGISTERED` — регистрация существующего профиля. `409 REGISTRATION_REQUIRED` — изменение незавершённого профиля. Регистрация и обновление предпочтений сериализуются блокировкой записи пользователя; предметы сохраняются в той же транзакции. Авторизационные и персональные ответы используют `Cache-Control: no-store`.
