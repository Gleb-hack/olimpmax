# Вход и профили пользователей

## Экраны

- `/welcome`: исходная иллюстрация из Figma, кнопки входа и регистрации.
- `/login`: повторный вход через текущий аккаунт MAX.
- `/register`: имя, класс (необязательно), интересующие предметы (необязательно).

Основа: Figma `Jms4ehBLLAgrGkFtm7G9js`, экраны «Добро пожаловать» (`69:99`), «Вход» (`71:99`), «Регистрация» (`78:131`). Иллюстрация экспортирована из слоя `68:886` в `apps/web/src/assets/olimp/welcome.png`. Цвета, поля, кнопки и переключатель перенесены из макетов; логин, пароль и восстановление пароля заменены подтверждением личности через MAX. Системная строка состояния телефона не имитируется.

## Как работает вход

1. Клиент получает `window.WebApp.initData` и отправляет его в `POST /auth/max`.
2. Сервер проверяет HMAC-SHA256, срок действия, повторяющиеся параметры и пользователя. Идентификатор MAX нельзя задать полем формы.
3. Сервер находит или создаёт техническую запись `user_profiles` по уникальному `max_user_id`. Возвращает часовой JWT и `UserProfile`; `registeredAt: null` означает незавершённый профиль.
4. Кнопка «Войти» открывает существующий зарегистрированный профиль; новому пользователю предлагается вкладка регистрации.
5. Регистрация отправляет `POST /me/registration`. Запись обновляется атомарно, `registeredAt` устанавливается один раз. Повторная регистрация возвращает `409`, не перезаписывая профиль.
6. Повторный вход с тем же MAX ID возвращает тот же внутренний UUID, профиль и план. Имя из MAX обновляется отдельно от имени, выбранного в Olimp.

Официальная схема проверки: https://dev.max.ru/docs/webapps/validation. Bridge: https://dev.max.ru/docs/webapps/bridge.

JWT хранится только в памяти страницы. При перезапуске сессия восстанавливается через проверенные стартовые данные MAX; в `sessionStorage` хранится лишь флаг входа/выхода, без токена. После выхода очищаются токен в памяти, кэш запросов, выбранные сравнения и переписка. Серверный профиль и план остаются. Уже выданный JWT действует до истечения часа; серверного списка отозванных сессий пока нет.

Защищённые страницы направляют на приветствие. При входе по прямой ссылке приложение возвращает пользователя к нужной странице. При истёкших стартовых данных нужно закрыть и открыть мини-приложение в MAX. Сетевые ошибки не включают деморежим автоматически.

## Профиль и база

Новая отдельная база не нужна: пользователи и олимпиады находятся в существующей PostgreSQL и связаны внешними ключами.

- `user_profiles`: UUID, уникальный MAX ID, имя из MAX, выбранное имя профиля, класс, город, предпочитаемые форматы, даты создания/регистрации/обновления.
- `user_subjects`: уникальная пара пользователь + предмет; предмет должен существовать в каталоге.
- `plan_items`: уникальная пара пользователь + олимпиада, заметка, отслеживание и дата сохранения.

`GET /me` читает профиль. `PATCH /me/profile` изменяет только разрешённые поля текущего пользователя. `userId`, `maxUserId`, время регистрации и неизвестные поля запрещены. Пользователь всегда определяется из проверенного JWT. Изменение предпочтений и списка предметов выполняется в одной транзакции.

Настройки профиля синхронизируются через сервер. Загруженное фото остаётся локально и хранится под внутренним UUID аккаунта. Старые локальные настройки не удаляются: в профиле есть предложение перенести их в аккаунт, если они найдены для подтверждённого MAX ID. Фото старого локального профиля продолжает отображаться.

Миграция `0002_kind_charles_xavier.sql` добавляет поля и таблицу предметов. Существующие аккаунты считаются зарегистрированными; UUID и все планы сохраняются. Для другой установки выполните `pnpm db:migrate` перед запуском обновлённого API. Автоматического удаления аккаунта и рассылки напоминаний нет.

## Локальная проверка

`pnpm db:local start`, `pnpm db:migrate`, `pnpm dev`.

На Vite dev-сервере `/auth/dev` использует один локальный тестовый аккаунт; API должен иметь `ALLOW_DEV_AUTH=true` и работать на loopback. В production этот вход запрещён, без MAX Bridge показывается инструкция открыть приложение в MAX. `VITE_DEV_AUTH=false` отключает локальную кнопку входа. `VITE_DATA_MODE=mock` включает отдельный демонстрационный профиль и план в браузере.

`pnpm test:integration` проверяет миграцию старого аккаунта с планом, создание профиля, повторную регистрацию, сохранность после перезапуска API, изоляцию пользователей, подмену ID, ограничения классов/предметов и одновременную регистрацию. Тесты используют отдельные временные базы и не меняют рабочий каталог.

Для проверки в настоящем MAX нужны серверный `MAX_BOT_TOKEN` и HTTPS URL мини-приложения, подключённый к боту. Локальные и подписанные тестовые сценарии не заменяют проверку запуска из мессенджера.
